# Инструкция для жюри

Как за 10 минут проверить систему по критериям хакатона. Запуск — в [README](../README.md):
архив датасета в `./data`, затем `docker compose up -d --build`.

## 1. Подать поток

По умолчанию поток подаётся **сам**. Сервис `replayer` читает исторический день 06.01.2026
(`validate/traffic.csv`) и для каждого из 30 бортов открывает своё TCP-соединение к backend. Дальше
он отправляет данные как настоящий терминал: handshake `NPH_SGC_CONN_REQUEST`, затем realtime-пакеты
с ячейкой `G6CellNav00` и исходными timestamp. Старт в 07:00 после прогрева 30 сим-минут, в реальном времени (×1).

Скорость переключается кнопками **×1 / ×10 / ×30 / ×60** рядом с часами на дашборде, там же
пауза. При ×30 инциденты появляются за минуту-две — удобно для быстрого просмотра.

То же через API (backend проксирует в replayer):

```bash
# пауза / продолжить
curl -X POST localhost:8000/api/v1/replay/control -H 'Content-Type: application/json' -d '{"action":"pause"}'
curl -X POST localhost:8000/api/v1/replay/control -H 'Content-Type: application/json' -d '{"action":"resume"}'
# скорость ×60
curl -X POST localhost:8000/api/v1/replay/control -H 'Content-Type: application/json' -d '{"action":"speed","speed":60}'
# перемотка на 17:30 (новая сессия с прогревом)
curl -X POST localhost:8000/api/v1/replay/control -H 'Content-Type: application/json' -d '{"action":"seek","seek_to":"2026-01-06T17:30:00"}'
```

Скорость по умолчанию и время старта задаются в `.env`: `REPLAY_SPEED` (по умолчанию 1), `REPLAY_START`.

**Официальный эмулятор NDTP.** Он показывает, что backend принимает «живой» NDTP от чужого источника:

```bash
docker load -i data/raw/ndtp-telemetry-emulator.tar
docker compose --profile emulator up -d
```

Конфиг `scripts/emulator_config.json` поднимает три борта (unitId 990001–990003, autoGenerate,
все ячейки) и направляет их на `backend:9201`. Этих бортов нет в расписании, поэтому они
появляются на карте серыми («неопознанный борт») и не получают прогнозов. Расписание и прогнозы
показывает replayer на исторических данных.

## 2. Где увидеть прогнозы и алерты

**Дашборд — http://localhost:8080.**

- **Верхняя полоса:** сим-время, режим потока (`Поток идёт` / `Прогрев` / `Поток прерван` / `Пауза` / `Нет источника`), число ТС
  по уровням риска, ТС на линии, открытые инциденты.
- **Карта:** маршрутная сеть, ТС с цветом и формой по риску (красный ▲ — опоздание > 2 мин или
  вероятность ≥ 50%, жёлтый ◆ — 1–2 мин, зелёный ● — в графике, синий ○ — опережение), стрелка
  курса. Проблемные перегоны подсвечены.
- **Лента инцидентов:** сортировка по «минут до события» и тяжести. Клик открывает карточку:
  - ТС и маршрут;
  - прогноз опоздания ± ожидаемая ошибка, вероятность опоздания;
  - «алерт создан за N мин до события»;
  - причина с доказательствами: вклады признаков, скорость на перегоне, простой;
  - участок маршрута, он выделяется на карте;
  - рекомендации и кнопка «Принять».
- После прохода целевой остановки инцидент закрывается фактом по GPS: «опоздание подтвердилось»
  или «не подтвердилось».
- **Drawer ТС** — клик по ТС на карте (или «Подробнее о ТС →» в карточке): нитка отклонения за
  час с прогнозом и интервалом, остановки ±60 мин (план / факт по GPS / прогноз).
- **Панель «Система»** — кнопка справа вверху: режим потока и ML, доля алертов с упреждением
  ≥ 10 мин и гистограмма упреждения, латентности по этапам, приём NDTP и последний пакет (hex по
  полям NPL / NPH / ячейки и раскодированные значения), ссылки на Swagger и документацию.

**То же через API** (Swagger: http://localhost:8000/docs):

```bash
curl -s localhost:8000/api/v1/vehicles | jq '.[] | select(.prediction) | {vehicle_id, risk_level, p: .prediction | {predicted_delay_s, p_late, lead_min, horizon_ok}}'
curl -s 'localhost:8000/api/v1/incidents?status=open' | jq '.[0]'
```

## 3. Горизонт 10–15 минут

- Каждую сим-минуту backend для каждого ТС прогнозирует **все** остановки с плановым временем в
  окне `(T+10, T+15]`. Поле `lead_min` — сколько минут от момента прогноза до планового прибытия,
  у прогнозов в окне оно всегда в (10, 15].
- Инцидент открывается только **до** события: время создания раньше планового прибытия на цель,
  это покрыто тестом `tests/test_backend_pipeline.py`. Если в окне нет остановок (перерыв,
  конечная), ставится `horizon_ok=false` и инцидент не открывается.
- Правило алерта: визит окна три прохода подряд держит «прогноз > 120 с или вероятность опоздания
  ≥ 0.5» — одиночные «мигающие» красные не беспокоят диспетчера. Пороги — `ALERT_DELAY_S`,
  `ALERT_P_LATE`, `ALERT_MODE`, `ALERT_MIN_STREAK` в `.env`; как подобраны —
  [perf/alert_policy.md](perf/alert_policy.md).
- Горизонт на потоке — `GET /api/v1/metrics/quality`: доля алертов с упреждением ≥ 10 мин,
  гистограмма упреждения, онлайн-MAE по закрытым инцидентам, precision и recall алертов.
- Сверка потока с реальной разметкой за весь день — [perf/stream_eval.md](perf/stream_eval.md):
  353/353 точки с прогнозом, 100% прогнозов в окне (10, 15], ни одного «задним числом», паритет
  офлайн/поток 0.03 с. Воспроизвести: `uv run python -m scripts.stream_eval` (~8 мин).

## 4. Приём NDTP и производные признаки

- `GET /api/v1/ingest/stats` — пакетов в секунду, CRC и ошибки разбора, соединения, реконнекты,
  «неопознанные» борта, **последний пакет** (hex и раскодированные поля).
- Сопоставление с расписанием и производные признаки: текущее отклонение от графика
  (`current_dev_s` у ТС), средняя скорость на перегоне и её отношение к типичной
  (`/api/v1/segments/risk`, `speed_ratio`), время простоя (`dwell`) — в доказательствах причины
  инцидента.

## 5. Надёжность и производительность

Цифры и методика — [PERFORMANCE.md](PERFORMANCE.md). Проверить вручную:

```bash
docker compose stop replayer   # обрыв потока: через 30 с режим «Поток прерван» (DEGRADED), сервис жив, карта по последнему состоянию
docker compose start replayer  # поток вернулся → LIVE
docker compose stop ml         # ML недоступен: прогнозы по эвристике, model_mode=fallback
docker compose start ml        # восстановление
./scripts/chaos.sh             # то же автоматически, с логом
./scripts/coldstart.sh         # холодный старт: время до healthy и до первого прогноза
```

Латентности (ingest→state, прогноз→WS, батч ML) видны на `GET /api/v1/metrics/summary` и в
Prometheus `/metrics`.

## 6. ML и сабмит

- Сабмит — `submissions/`, журнал с CV-метриками — [SUBMISSIONS.md](SUBMISSIONS.md).
- Модели и отчёт CV — `models/metrics.json`. Пересобрать: `uv run python -m services.ml.app.train`,
  затем `uv run python -m scripts.make_submission`.
- Дообучение ML-ядра в Docker без остановки системы (≈30 с):

  ```bash
  docker compose --profile train run --rm train --refit   # переобучить модели в ./models
  curl -X POST http://localhost:8001/model/reload          # ML подхватит их на лету
  ```

  Ответ reload показывает отпечатки моделей до и после. Без `--refit` — полное обучение с CV
  (≈20 мин). То же одной командой — `make retrain`.
- Сабмит воспроизводится **потоковой системой**: `uv run python -m scripts.make_submission_stream`
  проигрывает validate-день через backend (NDTP по TCP → признаки → ML-сервис) и пишет
  `submissions/sub_v4_stream.csv` из того, что поток выдал для точек validate (≈4 мин).
- Честность: признаки строятся только из телеметрии с `event_time ≤ T` и планового расписания.
  Найденную в данных утечку мы не используем — [DATA_AUDIT.md](DATA_AUDIT.md).
