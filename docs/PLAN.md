- **Что сдаём.** Сабмит `.csv`, ссылку на систему в Docker, инструкцию для жюри, документацию (Sphinx + Swagger), описание производительности и доп. фич.
- **Баллы.** Точность 6 (максимум уже при score ≥0.70), горизонт 4, система 6, дашборд 6, надёжность 4, питч 10.
- **Состояние.** Репозиторий `github.com/jinxovich/transit-pulse` пустой. Датасет лежит в `Downloads/Предиктор задержек транспорта.zip`, внутри вложенный `dataset.zip`.

## 3. Архитектура

```
 [ndtp-emulator :18080]──TCP NDTP──┐  (live-полоса: сим-часы не двигает, прогнозов нет)
 [replayer :8090]──TCP NDTP────────┤  (replay-сессия: двигает сим-часы)
          │ POST /internal/sim/session (start/seek/pause/speed)
          ▼                        ▼
 backend :8000 + NDTP :9201
   ingest (только кладёт в state) → state (кольцевые буферы на ТС)
   планировщик в thread-worker: каждую сим-минуту → as-of признаки → батч → ml :8001
   → риск + причина + рекомендации → инциденты → REST /api/v1 + WS /ws/v1/stream + /metrics + /code-docs
          ▼
 dashboard :8080 (nginx + React, проксирует /api и /ws)
```

- **Модули по ТЗ.** ingest/NDTP + API = `backend`, ML-ядро = `ml` (обучение + инференс, stateless), `dashboard`. В README это прямо сопоставлено с критерием.
- **Сим-часы по сессиям.**
  - Replayer сообщает бэкенду `session {id, start, speed, state}`. Новая сессия (loop или seek) очищает state и инциденты, клиентам уходит свежий WS `snapshot` с `session_id`.
  - Если пакетов нет: `sim_now = last_wm + (wall − wall_at_wm) × speed`. Часы идут дальше, ТС становятся stale, работает fallback.
  - DEGRADED определяется по wall-clock и только в состоянии `running`. Пауза не считается обрывом.
- **Live-полоса.** Пакет с timestamp вне `[day_start−1h, day_end+6h]` или с неизвестным `unitId` считается «неопознанным бортом»: он есть на карте и в статистике ingest, но часы не двигает и прогнозов не получает.
- **Хранилище.** In-memory, журнал прогнозов и инцидентов в SQLite для quality-метрик. Без Postgres и Kafka.

## 5. `transit_core` (TDD на критичном)

1. **`ndtp/`.** Кадр NPL(15) + NPH(10) + ячейки, little-endian, CRC-16/Modbus со свапом байт.
   - Потоковый фрейминг с ресинхронизацией по `0x7E7E` и частичными кадрами.
   - Битый CRC: пока логика CRC не подтверждена на реальных байтах эмулятора, **считаем и принимаем** такие пакеты.
   - Парсим Nav00 и 5 ячеек режима autoGenerate: IntSensor02 (26), Usi08 (6), Can10 (37), Termo16 (8), Lls15 (50). На неизвестном типе ячейки прекращаем разбор этого пакета без ошибки.
   - Ответ сервера необязателен, но отправляем.
   - **Эталонный тест** — захват реальных байт эмулятора (`emu.bin`) плюс roundtrip и пример из спеки.
2. **`schedule.py` / `trips.py`.** План без колонки факта. Рейсы режем по разрыву ≥5 мин. Паттерн = последовательность остановок, имя «первая ↔ последняя». Сегменты: P0 — прямые, P1 — по GPS-трекам.
3. **`matching.py`** (доп. фича map-matching). Проекция на полилинию рейса с монотонным прогрессом, курсом и штрафом за откат назад.
   - Учитываем специфику NDTP: `valid`-бит, нулевые координаты у невалидных точек, масштаб 1e7, целочисленные скорость и курс, GPS-выбросы (368 км/ч).
4. **`stops_detector.py`.** Виртуальный факт прибытия: вход в радиус 35 м или минимум дистанции ≤80 м с интерполяцией; плюс dwell.
   - MAE детектора против фактов train публикуем.
   - Здесь же `cur_dev_online` и метрика MAE(`cur_dev_online`, `cur_dev_s`).
5. **`labels.py`.** Генератор цели. **Тест: воспроизводит `labels_train`/`labels_test` 1:1.**
6. **`features.py`** — единый путь as-of. Офлайн-признаки строятся **прогоном строк CSV через тот же код state/ingest** в процессе, с тем же округлением, что в NDTP (секунды, 1e-7). Идентификаторы в признаки не идут. Группы:
   - **A. Расписание и подсказка:** `cur_dev` (hint или online), `lead_min`, час (sin/cos), `manual_fill` цели, цель — первая в рейсе, разрыв перед целью, число остановок до цели, разрыв рейса между сейчас и целью, максимальный разрыв, плановое время хода до цели, прогресс рейса.
   - **B. GPS:** скорость last/1/5/15 мин, доля стоянки, свежесть, доля невалидных, GPS-отклонение от нитки сейчас, виртуальные задержки на последних k остановках и их тренд, dwell.
   - **C. ETA:** остаток пути по маршруту / ожидаемая скорость. Ожидаемая скорость — по **своему** ТС и медиане дня по сегменту **только реальных** ТС, клоны исключаем.
7. **`causes.py`** (правила + вклады из CatBoost `ShapValues`), готово **26.09 вместе с алертами**:

   | Код | Смысл | Признак |
   |---|---|---|
   | `ACCUMULATED_DELAY` | Эффект домино | `cur_dev` высокий, тренд растёт |
   | `CONGESTION` | Затор на перегоне | Скорость на сегменте ≪ медианы дня, отклонение растёт |
   | `LONG_DWELL` | Долгая посадка / простой | dwell > p90 |
   | `SHORT_LAYOVER` | Мало запаса на конечной | Разрыв рейса до цели меньше текущего опоздания |
   | `EARLY_RUNNING` | Опережение графика | — |
   | `GPS_LOSS` | Нет данных от ТС | — |

   У каждого кода 1–3 рекомендации: сократить стоянку, подменный или резервный выпуск, связаться с водителем, объезд / ЦОДД, придержать на остановке.

## 6. ML-ядро (сознательно компактно)

**CV.** Повторяемый GroupKFold (3×5) по `(tr_id, блок)` на 1 494 реальных размеченных точках (реальные ТС из train + test). Синтетика есть только в обучающих фолдах. Отчитываемся двумя цифрами: с синтетикой и real-only. Отдельный holdout не нужен.

**Анти-утечка (pytest):**
- признаки инвариантны к порче строк телеметрии с `event_time > T`;
- построитель признаков не получает `time_fact_begin`;
- ни один `target_stop_id` из validate не попадает в обучающие цели;
- плотная разметка — P2, и то только если цель и все использованные факты лежат внутри одного train/test-блока.

**Модели:**
1. **v0 baseline** — проверка формата. **v1 LightGBM** — тот самый быстрый код, сегодня.
2. **v2 CatBoost** (CPU).
   - Остаток `y−cur_dev`, **MultiQuantile(0.1/0.5/0.9)**.
   - Медиана → прогноз; `p_late` — интерполяция квантилей относительно 120 с; «±ошибка» = (q90−q10)/2, сверяем с OOF-MAE по lead.
   - Вес синтетики подбираем на CV (0.3–1.0).
   - Сервим нативно (нужны `ShapValues`).
3. **GRU (лимит 3 ч, 26.09 вечер, GPU).**
   - Вход: последние 20 мин на сетке 15 с + признаки A.
   - Экспорт в ONNX, в сервинге только `onnxruntime`, без torch.
   - В ансамбль (веса по OOF) берём, только если OOF улучшился. Иначе честно пишем «прироста не дал». Не влит к 23:00 26.09 — выбрасываем.
4. **Две версии признаков.** Submission-модель использует `cur_dev_s`, stream-модель — `cur_dev_online`.
   - Паритет проверяем так: stream-модель офлайн против stream-модели на потоке на точках `labels_test`.
   - Stream-MAE хуже submission-MAE **по построению**: `cur_dev_s` содержит факты, наступившие после T. Так и объясняем.
5. **Финальное обучение** на train+test, число итераций = 1.1 × среднего лучшего на CV.
6. **Сабмиты.** В зачёт идёт лучший за всё время, лимит 24 успешных в сутки.
   - `make_submission` + `validate_submission`: 151 строка, `;`, без NaN и дублей.
   - Лог в `docs/SUBMISSIONS.md`.
   - Модель для питча выбираем **по CV**, лидерборд нужен для страховки (на 151 точке его шум около ±0.1 score).
7. **Анализ для питча.** Профили скорости и отклонения до `late` против `ontime`, эффект разрыва рейса и `manual_fill`, MAE стоп-детектора.

## 7. Backend (FastAPI + asyncio)

- **ingest.** TCP :9201, только парсинг и запись в state (bounded queue: при переполнении выкидываем старое и считаем).
  - `/api/v1/ingest/stats`: пакетов в секунду, CRC-ошибки, реконнекты, последний пакет hex + поля.
- **state.** Кольцевые буферы 60 мин, `unit_map`, план дня (`validate/schedule_plan.csv`), сим-часы и сессии (раздел 3).
- **pipeline** (thread-worker, numpy). Каждую сим-минуту для каждого ТС:
  - прогнозы на все остановки в `(T+10,T+15]`;
  - «первая в окне» идёт в карточку ТС и в паритет-лог;
  - пустое окно (перерыв) → `horizon_ok=false`, **инцидент не открываем**.
- **Прогрев.** После старта или новой сессии replayer отдаёт предыдущие 30 сим-минут на максимальной скорости. Пока истории < 15 мин, ТС помечено `warming_up`, инциденты подавляются.
- **alerts.** Пороги согласованы с классами организаторов, приходят из `/config`:
  - red — `pred > 120` или `p_late ≥ 0.5`;
  - yellow — `60–120` или `p_late` 0.3–0.5;
  - green — остальное;
  - early — `pred < −60`, отдельный маркер.

  Жизненный цикл: `open → ack → resolved`. Resolved — по виртуальному факту прибытия, исход `hit` / `false_alarm` / `miss`. Дедупликация по ТС и рейсу. Инциденты в WS отправляем **сразу**, не дожидаясь дельты раз в секунду.
- **quality.** Онлайн-MAE, доля алертов с упреждением ≥10 мин (цель 100%), гистограмма упреждения, precision/recall.
- **degrade.**
  - Поток пропал на 30 с wall-clock при `running` → DEGRADED: fallback «расписание + последнее состояние», бейдж.
  - Поток вернулся → LIVE.
  - ML недоступен → circuit breaker и эвристика `0.7·cur_dev`, `model=fallback`.
- **metrics.** Prometheus: ingest→state и pass→WS (p50/p95), лаг очереди, размер батча, латентность ML.
- **P2 / роадмап:** what-if (`POST /whatif` — «придержать ТС», «сократить стоянку»), восстановление из снапшота, hot-swap модели через `POST /train`.

## 8. Источники потока

- **replayer** (главный).
  - Читает `validate/traffic.csv` **в порядке `event_time`** и кодирует Nav00 с исходным timestamp. На каждый unit — своё TCP-соединение с handshake.
  - **Автостарт** по пресету из env: `REPLAY_START=07:00`, `SPEED=30`, `LOOP=1`, плюс прогрев 30 мин.
  - HTTP-управление `start / pause / speed / seek` и `fleet_multiplier` для нагрузочного теста.
  - О каждом изменении сообщает бэкенду: `POST /internal/sim/session`.
- **Официальный эмулятор** (профиль `emulator`).
  - `scripts/emulator_config.json` использует unitId **вне** `unit_map` и `targetHost=backend`.
  - В JURY_GUIDE прямо: «эмулятор доказывает ingest NDTP, replayer показывает прогнозы на истории».
- **26.09, 09:00 — первая задача на Docker-машине.** Эмулятор (autoGenerate, все ячейки) → сырой приёмник → `emu.bin` в тестовые фикстуры.

## 9. Контракт (фиксируем 25.09; pydantic → OpenAPI + JSON Schema для WS → TS)

**REST `/api/v1`:**
- `health`, `config` (пороги, цвета), `network` (остановки, паттерны с GeoJSON, bbox);
- `vehicles`, `vehicles/{vehicle_id}` (прошедшие и будущие остановки: план / вирт. факт / прогноз, ряд отклонения);
- `incidents?status=`, `incidents/{id}`, `POST incidents/{id}/ack`;
- `segments/risk`, `metrics/summary`, `metrics/quality`, `ingest/stats`;
- `replay/control`, `sim/clock`.

**WS `/ws/v1/stream`:**

| Сообщение | Когда |
|---|---|
| `snapshot` | При подключении и при новой сессии |
| `vehicles.delta` | 1 Гц |
| `incident.opened / updated / resolved` | Сразу по событию |
| `kpis` | Раз в 2 с |
| `system.status` | LIVE / DEGRADED / OFFLINE / WARMING_UP |
| `ping` | Раз в 10 с |

В каждом сообщении есть `schema_version`, `session_id`, `sim_time`.

**Типы:**
- **`VehicleState`**:
  - идентификация: `vehicle_id` (`tr_id` или `"u:<unit_id>"`), `kind` (`scheduled` | `no_schedule` | `unknown`);
  - положение: `lon`, `lat`, `heading`, `speed_kmh`;
  - статус: `last_seen`, `stale`, `warming_up`, `current_dev_s`, `next_stop`;
  - `prediction` (nullable): `target_stop{id,name,lon,lat,planned_at}`, `predicted_delay_s` (**+ = опоздание**), `p_late`, `interval[q10,q90]`, `expected_abs_error_s`, `lead_min` (= `planned_at − generated_at`, в сим-минутах), `generated_at`, `horizon_ok`, `model_version`, `risk_level`, `cause_code`.
- **`Incident`**: `id`, `vehicle_id`, `route_name`, `status`, `risk_level`, `created_at`, `lead_min`, `target_stop`, `predicted_delay_s`, `p_late`, `interval`, `cause{code,title,details,evidence[{feature,label,value,contribution}]}`, `segment{from,to,geometry}`, `recommendations[]`, `actual_delay_s`, `outcome`.
- **Время** — naive ISO-строки (`"2026-01-06T07:14:00"`).
