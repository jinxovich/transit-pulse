# Реализованные возможности

Сначала — дополнительные фичи из ТЗ, затем то, что мы сделали сверх обязательного. У каждого пункта
указано, где он в коде и чем подтверждён.

## Дополнительные фичи из ТЗ

### 1. Map Matching с учётом специфики NDTP

`packages/transit_core/transit_core/matching.py`, `route_line.py`; в backend — на каждой точке ingest.

- Нитка рейса — полилиния по плановым остановкам с накопленной дистанцией и плановым временем.
  Точка проецируется на неё с **монотонным прогрессом**. Кандидат выбирается по поперечному
  расстоянию, штрафу за откат, согласию курса с азимутом отрезка и слабому приору расписания.
- Специфика NDTP:
  - точки с `valid=0` (бит `extraDopBit7`) и нулевыми координатами считаются «нет данных»;
  - скачки быстрее 120 км/ч и «телепорты» после разрыва связи отбрасываются;
  - стоянка (скорость < 3 км/ч, дрожание GPS) не двигает прогресс;
  - точки не по порядку не сбивают якорь;
  - смена рейса на конечной определяется по плану и проекции.
- Из привязки считается **отклонение от нитки графика между остановками**: плановое время для
  текущего прогресса против сим-времени. Оно идёт в `current_dev_s` ТС, ряд отклонения и следующую
  остановку.
- Качество на 13 реальных ТС (`models/matching_metrics.json`):
  - 90.7% валидных точек привязаны к маршруту, поперечное отклонение — медиана 12.9 м;
  - 0 откатов на 66 546 шагах;
  - отклонение в момент прибытия: MAE **19.4 с** против 36.6 с у отклонения по последней остановке;
  - 34 мкс на точку, p99 — 102 мкс.

### 2. What-if анализ

`POST /api/v1/whatif`, `services/backend/app/whatif/`; на дашборде — блок «Что если…» в карточке
инцидента.

- Меры:
  - «придержать на остановке N мин»;
  - «сократить отстой на конечной N мин»;
  - «выпустить без отстоя»;
  - «резервный выпуск» — подменное ТС, отклонение рейса после конечной сбрасывается.
- Для каждой остановки ближайшего часа система пересчитывает признаки с учётом меры и прогоняет
  их через ту же модель. Ответ: «было → стало» по опозданию, вероятности и уровню риска.
- Монотонный фильтр не даёт модели выдать абсурд: «придержать» не уменьшает задержку, меры на
  конечной её не увеличивают. Если мера неприменима (в ближайший час нет конечной), ответ говорит
  об этом прямо.

### 3. Оптимизация инференса: ONNX и latency

- Модель последовательностей (GRU) экспортирована в **ONNX** (`models/gru.onnx`, opset 17,
  динамический batch). Инференс идёт через onnxruntime без PyTorch. Паритет с PyTorch — 6·10⁻⁵ с.
  Латентность: 2 мс на ТС, 32 мс на батч 30.
- CatBoost-прогноз: 1.5 мс на батч 30. Дорогие SHAP-объяснения считаются только для рискованных
  прогнозов, поэтому батч ML на потоке сократился со 111 до 57 мс p50. Подробнее —
  [PERFORMANCE.md](PERFORMANCE.md).

### 4. Ансамбль: CatBoost для табличных признаков + PyTorch GRU для последовательностей

- GRU (2 слоя, hidden 64) читает последние 20 минут телеметрии на сетке 15 с и статические
  признаки расписания. Обучение — на **GPU (RTX 3080, CUDA)**, 5 моделей, среднее.
- Веса подобраны по OOF на общих фолдах: сабмит v2 = 0.85·CatBoost + 0.15·GRU.
  - OOF-MAE 51.9 против 52.1 у одного CatBoost.
  - Прирост небольшой, корреляция ошибок моделей 0.86. Мы это честно указываем в
    [SUBMISSIONS.md](SUBMISSIONS.md).

## Сверх обязательного

### ML-ядро

- **Квантильная регрессия** CatBoost (q10 / q50 / q90) на остатке к текущему отклонению.
  - Интервал откалиброван по OOF конформно, отдельно для каждой минуты упреждения: покрытие 80% на
    каждом горизонте (сырые квантили покрывали 44%, на 13–15 мин при общем множителе — 65%).
  - Вероятность опоздания > 2 мин откалибрована изотонической регрессией: Brier 0.154 → 0.140,
    ECE 0.111 → 0.033 (кросс-фит на OOF). Отчёт — `models/metrics.json` → `calibration`.
- **Политика алертов подобрана реплеем** всего дня на честных прогнозах
  ([perf/alert_policy.md](perf/alert_policy.md)): инцидент — после трёх проходов подряд с прогнозом
  > 2 мин или p_late ≥ 0.5. Ложных алертов меньше: 1.24 → 0.86 на ТС в час, точность 41% → 49%,
  85% опоздавших рейсов по-прежнему с алертом, упреждение 100% ≥ 10 мин. Пороги — в `.env`.
- **Проверенные и отброшенные идеи** записаны с цифрами: отклонение по нитке (map-matching) как
  признак stream-модели дало −1.3 с MAE при пороге внедрения 2 с
  (`models/sched_dev_experiment.json`); GRU в ансамбле — −0.2 с.
- **Честная кросс-валидация** 3×5 GroupKFold по (ТС, 30-минутный блок) с защитой от
  синтетических клонов. Отчитываемся тремя цифрами: с синтетикой, real-only и наивно —
  [DATA_AUDIT.md](DATA_AUDIT.md).
- **Две модели:**
  - submission — на подсказке организаторов `cur_dev_s`;
  - stream — на отклонении, посчитанном онлайн по GPS; её и использует поток.
- **Объяснимость:** SHAP-вклады признаков превращаются в причину сбоя из справочника (накопленное
  опоздание, затор на перегоне, долгая стоянка, мало запаса на конечной, опережение, потеря GPS)
  с доказательствами и рекомендациями диспетчеру.
- **Виртуальные факты прибытия по GPS** (стоп-детектор): MAE 15.5 с против факта организаторов,
  медиана 4.3 с. По ним закрываются инциденты («опоздание подтвердилось / не подтвердилось») и
  считается онлайн-качество.

### Поток и backend

- **Собственный NDTP-кодек** — все шесть ячеек режима autoGenerate. Байт-в-байт совпадает с
  официальным эмулятором, CRC подтверждён на реальном захвате (`tests/fixtures/emu.bin`).
  Потоковый декодер с ресинхронизацией по `0x7E7E`.
- **Replayer:** исторический день проигрывается как настоящий NDTP-трафик. У каждого борта своё
  TCP-соединение с handshake, есть пауза, скорость ×1–600, перемотка с прогревом, цикл и
  `FLEET_MULTIPLIER` для нагрузки.
- **Официальный эмулятор** подключается профилем `emulator`. Его борта — «неопознанные»: видны
  на карте и в статистике, прогнозов не получают.
- **Производные признаки на потоке:**
  - текущее отклонение (по привязке к нитке);
  - средняя скорость на перегоне и её отношение к типичной, где типичная — медиана реальных ТС
    по историческим данным;
  - время простоя на остановке.
- **Горизонт:** прогнозируются все остановки окна (T+10, T+15]. Инцидент не открывается
  «задним числом», упреждение каждого алерта видно в карточке и в `/metrics/quality`.
- **Надёжность:**
  - DEGRADED по wall-clock с fallback «расписание + последнее состояние»;
  - circuit breaker на ML;
  - реконнект бортов после рестарта backend;
  - bounded queue на ingest.
- **Наблюдаемость:** Prometheus `/metrics` в backend и ML, латентности ingest→state,
  прогноз→WS и батча ML, журнал прогнозов и инцидентов в SQLite, последний NDTP-пакет
  (hex и поля) на `/api/v1/ingest/stats`.

### Дашборд

React + MapLibre. Риск кодируется **цветом и формой** маркера, есть стрелка курса. Проблемные
перегоны подсвечены. Лента инцидентов отсортирована по «минут до события». Карточка инцидента
содержит упреждение, причину с доказательствами, участок на карте, рекомендации с кнопкой
«Принять» и what-if. Обновления идут в реальном времени по WebSocket, есть баннеры режимов
потока и реконнект с backoff.
