# Производительность и надёжность

Все цифры сняты 27.09 на демо-машине: 12 ядер, 31 ГБ RAM, RTX 3080, Docker Compose. Стек поднят
командой `docker compose up -d`. Сырые логи лежат в [`docs/perf/`](perf/), каждый замер
повторяется одной командой из раздела «Как воспроизвести».

## Коротко

| Что | Результат |
|---|---|
| Latency инференса ML, батч 30 ТС | **1.5 мс** без объяснений, 135 мс p50 с SHAP-вкладами |
| Приём пакета NDTP → state | p95 **0.7 мс** при 30 бортах, **7.5 мс** при 300 |
| Прогноз → WebSocket (весь проход сим-минуты) | p95 **0.25 с** при 30 бортах, **0.44 с** при 300 |
| Пропускная способность | 300 TCP-соединений, в среднем 757 пакетов/с, пик 3 390, **0 потерь, лаг очереди 0** |
| Обрыв потока | Сервис жив, через 30 с режим DEGRADED, прогнозы по последнему состоянию; после реконнекта сразу LIVE |
| Падение ML-сервиса | Circuit breaker → эвристика `0.7·cur_dev` (`model_mode=fallback`); восстановление ≤ 10 с |
| Рестарт backend | Все 30 бортов replayer переподключаются сами, поток и прогнозы восстанавливаются |
| Холодный старт | Все контейнеры healthy за **17.5 с**, первый прогноз через **17.6 с** |

Ориентир ТЗ — меньше 1–2 с на поток ТС. Полный путь «пакет → прогноз на дашборде» укладывается
в 0.5 с даже на ×10 парке.

## 1. Латентность ML-сервиса

`POST /predict` на реальных признаках validate, 50 повторов на каждый размер батча
(`scripts/bench_ml.py`). Модель — CatBoost stream, вклады признаков — точный SHAP CatBoost.

| Батч | Без объяснений, p50 / p95 | С вкладами (SHAP), p50 / p95 |
|---|---|---|
| 1 | 0.6 / 0.8 мс | 30 / 42 мс |
| 30 | 1.5 / 1.8 мс | 135 / 181 мс |
| 300 | 4.6 / 8.9 мс | 310 / 457 мс |

Это время на сервере; с HTTP клиент видит на 2–10 мс больше. Сам прогноз дешёвый, почти всё время
уходит на объяснения. Вклады нужны только в карточке инцидента, поэтому их можно запрашивать лишь
для ТС с высоким риском (`explain: false` для остальных).

**GRU в ONNX** (`models/gru.onnx`, onnxruntime CPU, среднее 5 моделей): батч 1 — 2.0 мс, батч 30 —
32 мс, батч 300 — 365 мс p50. Паритет с PyTorch — 6·10⁻⁵ с.

## 2. Backend на потоке

Метрики снимаются самим backend: Prometheus `/metrics` и `GET /api/v1/metrics/summary`.

| Этап | 30 бортов, ×30 | 300 бортов, ×60 |
|---|---|---|
| Пакет NDTP → state (`ingest_to_state`), p50 / p95 | 0.3 / 0.66 мс | — / 7.5 мс |
| Проход прогнозов → отправка в WS (`pass_to_ws`), p95 | 248 мс | 435 мс |
| Батч ML (`ml_batch`), p50 / p95 | 111 / 152 мс | — / 176 мс |
| Лаг очереди ingest | 0 | 0 |
| Потерянные пакеты | 0 | 0 |

Как устроено: ingest только разбирает кадр и кладёт точку в кольцевой буфер ТС (bounded queue;
при переполнении выбрасываем старое и считаем). Прогнозы строятся в отдельном worker-потоке раз в
сим-минуту одним батчем на все ТС, поэтому медленный ML не тормозит приём.

## 3. Пропускная способность (loadtest)

`scripts/loadtest.py --fleet 10 --speed 60`: replayer клонирует каждый из 30 бортов 10 раз
(300 TCP-соединений, у каждого свой handshake и поток) и проигрывает день со скоростью ×60. Это
~20 пакетов/с на борт — на порядок чаще реального терминала (раз в 10–15 с).

- Средний поток — 757 пакетов/с, пик 3 390 пакетов/с (прогрев на ×600).
- 300 соединений держатся весь прогон, 0 потерь, лаг очереди 0.
- Сырые замеры — [`perf/loadtest.json`](perf/loadtest.json).

Оговорка: клоны не входят в расписание, поэтому backend видит их как «неопознанные борта». Они
нагружают приём, state, карту и WebSocket, но не ML. Масштаб ML виден по таблице раздела 1: батч
300 без объяснений — 4.6 мс.

## 4. Деградация и восстановление (chaos)

`scripts/chaos.sh` гасит replayer на 60 с, потом ML-сервис на 30 с и раз в 10 с снимает состояние.
Лог — [`perf/chaos.log`](perf/chaos.log).

| Сценарий | Что происходит |
|---|---|
| Поток оборван, 0–30 с | Сервис отвечает, все ТС помечены `stale`, прогнозы переходят на fallback «расписание + последнее известное состояние» |
| Поток оборван, 30 с и дольше | Режим **DEGRADED** (`/health` → `degraded`, баннер на дашборде), данные не пропадают с карты |
| Поток вернулся | Через ≤ 10 с режим LIVE, прогнозы снова от ML |
| ML недоступен | `ml: down`, circuit breaker (3 ошибки → пауза 15 с) → эвристика `0.7·cur_dev`, `model_mode=fallback`; поток и карта работают |
| ML вернулся | Через ≤ 10 с прогнозы снова `model_mode=ml` |
| Backend перезапущен | Replayer переподключает все 30 бортов с backoff и повторяет handshake. Проверено вручную, реконнект покрыт тестом `tests/test_replayer_link.py` |

Пауза в replayer (`POST /api/v1/replay/control {"action":"pause"}`) — это не обрыв: режим PAUSED,
DEGRADED не включается.

## 5. Холодный старт

`scripts/coldstart.sh`: `docker compose down`, затем `up -d` на собранных образах. Лог —
[`perf/coldstart.log`](perf/coldstart.log).

| Сервис | Healthy через |
|---|---|
| ml (загрузка моделей и прогревочный батч) | 11.9 с |
| backend (план дня, сеть, типичные скорости; ждёт healthy ml) | 12.0 с |
| replayer | 17.4 с |
| dashboard | 17.5 с |
| **Первый прогноз на потоке** | **17.6 с** |

Порядок старта задан через `depends_on: service_healthy`. У каждого сервиса есть healthcheck.
`data-init` один раз распаковывает архив и при повторных стартах завершается мгновенно. Прогрев
предсказуемый: replayer проигрывает 30 сим-минут до старта на ×600 (≈ 3 с), backend не открывает
инцидентов, пока у ТС меньше 15 сим-минут истории. Первая сборка образов занимает несколько минут
и зависит от сети.

## 6. Масштабируемость

- **ML-сервис stateless**: признаки приходят в запросе, модели загружаются при старте. Инференс
  масштабируется репликами за балансировщиком без изменений кода. Дообучение — `train.py` пишет
  новые артефакты в `models/`, сервис подхватывает их при рестарте.
- **Backend**: приём и прогнозы разделены очередью; батч ML — один на сим-минуту на все ТС.
- **Узкое место** при росте парка — SHAP-объяснения (раздел 1). Их нужно считать только для
  рискованных ТС.

## Как воспроизвести

```bash
docker compose up -d
./scripts/coldstart.sh                                   # холодный старт
./scripts/chaos.sh                                       # деградация и восстановление
uv run python -m scripts.loadtest --fleet 10 --speed 60  # нагрузка
uv run python -m scripts.bench_ml --url http://127.0.0.1:8001 --batches 1 30 300
curl -s localhost:8000/api/v1/metrics/summary | jq       # текущие латентности
```
